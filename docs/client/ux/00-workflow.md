# UX 工作流：调研 → 设计 → 计划 → 验收

> 这份文档规定**每个 UX 模块**怎么从"现状很乱"走到"可以交付"，以及我和 CC（Claude Code）
> 在每个阶段各自干什么。模块清单与进度见 [UX 索引](./INDEX.md)。
>
> 为什么要有它：2026-11-10 那次我直接把十个步骤的旅程画成一张图就想开工，被 PO 打回 ——
> 因为 UX 不是一条线，是**十来个模块各自一套触点**，混在一起设计必然漏。
> 从这版起：一个模块一份文档，四阶段齐全才算设计完成。

---

## 1. 四阶段，每阶段有明确的"产物"和"出口条件"

| 阶段 | 要回答的问题 | 产物（写进模块文档的哪一节） | 出口条件（不满足不许进下一阶段） |
|---|---|---|---|
| **R 调研** | 这个模块现在**实际**对玩家说了什么、让玩家按了什么？ | §1 现状：触点数、通道、键位、文案、失败分支，每条带 `文件:行` | 数字是**扫出来的**不是估的；至少 3 条"玩家会卡住"的具体场景 |
| **D 设计** | 目标状态下，玩家每一步看到什么、能按什么？ | §2 设计：流程图 + 触点表（通道 / 键位 / 文案 / 时长） | 每个触点都能回答"为什么是这个通道"；没有"视情况而定" |
| **P 计划** | 改动拆成哪些可独立验收的小步？ | §3 计划：任务表（文件 / 改动 / 风险 / 验收方式） | 每步都能单独回滚；每步都有对应的闸门或真机步骤 |
| **V 验收** | 怎么证明玩家体验真的变了？ | §4 验收：可重复步骤 + 期望现象 + 反例 | 步骤是"按键/点按"级别的，不是"看看效果" |

> **红线**：四节缺任何一节，这份模块文档就是 `status: draft`，不许进仓库的"已设计"清单。

## 2. 我和 CC 的分工

| 阶段 | 我做 | CC 做 | 为什么这么分 |
|---|---|---|---|
| R 调研 | 写扫描脚本拿硬数字（调用点数、热区数、键位分布）；真机验证 | 读代码补"为什么会这样"（调用链、回调、状态机） | 数字要可复现；因果链要人读代码 |
| D 设计 | 定规则（通道边界、键位语义、优先级） | 提反对意见："这条规则和现有实现冲突" | 规则要对产品负责；冲突要有人挑刺 |
| P 计划 | 拆阶段、定验收 | 逐文件确认改法与风险（`文件:行`） | 计划要能执行；改法要贴代码 |
| V 验收 | 真机跑步骤、看日志与 DB | 只读复核："你验证的真的是那条分支吗" | 真机只有我这边有；复核要独立 |

**CC 任务书的写法规矩**（三次 `error_max_turns` 换来的）：

1. **点名 3–8 个具体路径**，不要写"全仓库找"；
2. 写清"已知事实，别再挖 X"；
3. **一轮只问一个问题**，输出上限写死（字数/表格行数）；
4. 需要它给"依据"就明说 `文件:行`，否则它会给一段听起来对的总结。

## 3. 触点的四种通道（所有模块共用）

| 通道 | 实现 | 什么时候用 |
|---|---|---|
| `feed` | `exports['custom-notify']:Push(src,'feed',title,body)` | 玩家动作**成功**了，要留个结果 |
| `toast` | 同上 `'toast'` | 玩家没主动做但影响他（案件、罚款、濒死） |
| `error` | 同上 `'error'` | 动作**没生效**（钱不够/冷却/没权限/太远） |
| `phone` | 同上 `'phone'` | IC 内容（消息、报警、调度、入账凭证） |

交互提示只用 `custom-prompt`：`Show({key='E',label=...})`（准星下方单条）、
`SetContext({{key,label},...})`（右侧 ≤3 条）。

**铁律**：一个交互物件只有一个入口；`error` 永不 toast；IC 内容永不上屏。
