# 01 — 预设→涌现漏斗：如何让预设任务成为涌现式玩法的入口

> **核心命题**: 预设内容和涌现式玩法不是二选一，是漏斗关系——预设内容保底，把玩家推进涌现式系统，涌现式系统培养所有权感。  
> **前置阅读**: [00 — 所有权哲学](00-ownership-philosophy.md)

---

## 1. 问题诊断: 大多数服务器的预设任务是"死胡同"

传统做法:

```
玩家接任务 → 完成任务 → 拿奖励 → 结束
```

这是"死胡同"——任务闭环在系统内部，玩家做完就走，没有产生任何社交、互赖、或世界后果。

**正确做法**:

```
玩家接任务 → 任务过程引入真人交互 → 系统检测社交行为 → 推荐组织/角色 → 滑入涌现式系统
```

---

## 2. 漏斗三层结构

```
┌─────────────────────────────────────────┐
│ 第一层: 引导任务（单人 + 学习玩法）       │
│ 目标: 学会基本操作，获得第一个"角色"      │
│ 时长: 1-3小时                             │
├─────────────────────────────────────────┤
│ 第二层: 桥接任务（必须与真人交互）         │
│ 目标: 建立第一个互赖关系                   │
│ 时长: 1-2周                               │
├─────────────────────────────────────────┤
│ 第三层: 涌现系统（玩家自己创造玩法）       │
│ 目标: 产生不可替代性 → 所有权感            │
│ 时长: 无限                                │
└─────────────────────────────────────────┘
```

**核心逻辑**: 第一层是饵，第二层是桥，第三层是终点。大多数服务器只有第一层——做了个精致的饵，没有桥。

---

## 3. 第一层: 引导任务的设计约束

| 约束 | 说明 |
|:---|:---|
| 每个任务≤10分钟 | 防止新手疲劳 |
| 任务链≤5个 | 做完刚好解锁第一个核心能力 |
| 不做"杀N只怪" | 每步教一个核心操作（开车、使用物品、找到工作点、与人对话） |
| 结尾不直接发钱 | 结尾发"介绍信"或"推荐"——指向第二层 |

**关键反直觉设计**: 引导任务的奖励不是钱或物品，而是**一个方向**。比如:

> "你已经学会修车基础。附近的修车铺 [Auto Clinic] 正在招学徒，过去跟他们的老板 [玩家名] 聊聊。"

这就把玩家从"系统NPC"的手里移交到了"真人"的手里。

---

## 4. 第二层: 桥接任务的设计模式

桥接任务的唯一目标是让玩家与至少一个真人建立互赖。以下是三个设计模式：

### 模式 A: 师徒任务

- 老玩家可以接"带新人"任务，获得声誉奖励（非物质奖励）
- 新人任务列表里有"请一位老玩家教你XX"
- 系统随机匹配（同职业、同在线时段），但允许指定

**关键**: 系统跟踪"师徒关系"的持续时间。如果某个师徒关系超过30天，系统赠予双方一个不可购买的"师徒铭牌"——这是所有权感的种子。

### 模式 B: 供需对接

- 新人生产的东西（如低级修理、基础采矿）正好是老玩家的消耗品
- 系统主动推送: "玩家[新人]正在出售XX，您需要吗？"
- 完成第一笔玩家间交易 → 解锁"商人"标识

### 模式 C: 事件共历

- 某些世界事件（如警察追捕、区域封锁）需要多人协作
- 新手会被自动分配到一个"需要帮忙"的事件组
- 完成事件后，系统建议互加为"联系人"（轻量级社交绑定）

---

## 5. 第三层: 滑入涌现式系统

当系统检测到以下信号时，自动触发"滑入"推荐：

| 信号 | 推荐动作 |
|:---|:---|
| 玩家与同一个真人交易>5次 | 推荐双方建立"商业伙伴"关系 |
| 玩家在同一区域停留>10小时（累计） | 推荐该区域的玩家组织 |
| 玩家被其他玩家@>10次（在Discord或游戏内） | 推荐创建或加入帮派 |
| 玩家完成某个职业技能树50% | 推荐"师傅"身份——你可以带新人了 |
| 玩家连续在线>30天 | 解锁"社区议会"投票资格 |

## 6. 系统架构要求

### 6.1 任务系统不能是封闭的

传统任务系统:
```
TaskManager: 接任务 → 检查条件 → 完成任务 → 发奖励
```

漏斗任务系统:
```
TaskManager:
  接任务 → 检查条件 → 完成任务
    ↓ (每个任务步骤都可能触发)
  社交检测器: 检查"这一步有没有产生真人交互？"
    ↓ 如果有
  漏斗引擎: 累积社交信号 → 达到阈值 → 触发推荐
    ↓
  推荐管道: 生成推荐 → 推送到玩家UI → 可选一键加入
```

### 6.2 需要的底层数据

```lua
-- Player metadata 新增字段
{
  social_signals = {
    player_trades = { [target_citizenid] = count },
    coop_events = { [event_id] = timestamp },
    mentor_id = nil,  -- 当前师傅的 citizenid
    apprentices = {}, -- 徒弟列表
    region_hours = { [region_id] = hours },
    mentions_received = count,
  },
  funnel_stage = 1,   -- 1=引导, 2=桥接, 3=涌现
  funnel_recommendations = {}, -- 当前活跃推荐
}
```

### 6.3 需要的新 Bus Service

```lua
Bus.RegisterService('funnel', {
  -- 记录一次社交事件
  RecordSocialSignal = function(citizenid, signal_type, data) end,
  -- 检查是否触发推荐
  CheckThresholds = function(citizenid) end,
  -- 获取当前推荐
  GetRecommendations = function(citizenid) end,
  -- 接受一条推荐
  AcceptRecommendation = function(citizenid, recommendation_id) end,
})
```

## 7. 与现有 T-City 系统的对接

| 现有系统 | 漏斗对接方式 |
|:---|:---|
| Quest 系统 (custom-quest) | 每个 quest 完成后调用 `Bus.funnel:RecordSocialSignal` |
| Job 系统 | 选择职业时触发信号记录 |
| Organization/帮派 | 加入时自动推进 funnel_stage=3 |
| Phone (custom-phone) | 联系人功能触发互赖信号 |

**最小可行实施**: 先在 quest 系统的奖励发放处插入一个钩子——任务完成时，检查玩家在任务过程中是否与真人交互过。这个钩子只需要 30 行代码，不改变任何现有逻辑，但为后续漏斗引擎提供了数据源。

---

## 8. 成功指标

| 指标 | 当前现状（典型值） | 目标值 |
|:---|:---|:---|
| 新手→首次真人交互时间 | 通常>3天 | <30分钟 |
| 新手→加入组织时间 | 通常>2周或无 | <3天 |
| 桥接任务完成率 | 无此概念 | >60% |
| 从漏斗进入涌现阶段的玩家比例 | 纯自然发生 | >40% |
