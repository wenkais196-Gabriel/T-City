# T-City Lite 银行系统安全净化与对账重构文档 (v0.3)

本文档记录了对 `qb-banking` 资源进行对账流水串卡漏洞（Transaction Statement Ghosting）的深度修复，以及物理银行卡（Debit Cards）与自动取款机（ATMs）系统的完全净化下线标准及测试验证规程。

---

## 1. 技术背景与漏洞分析 (Technical Overview & Bug Diagnosis)

在 v0.2 版本中，我们接到了玩家关于**子账户交易记录异常混淆**（明明新创建的账户只有 $100 余额，却离奇出现一条历史上的 $1000 交易记录）的故障报告。经过对 `qb-banking` 服务端内存模型及数据库同步机制的联合审计，我们发现了如下严重的技术实现偏差：

### 1.1 内存分区存储不一致漏洞

在 `server.lua` 中，对账流水（Statements）的内存对象在**游戏内实时交易时**与**服务器冷启动加载时**采用了完全不同的键值路径划分：

1. **游戏运行期间 (CreateBankStatement)**：
   ```lua
   -- 当 accountType 为 'player' (Checking) 或 'shared' (子账户) 时
   if accountType == 'player' or accountType == 'shared' then
       if accountType == 'player' then account = 'checking' end
       if not Statements[citizenid] then Statements[citizenid] = {} end
       if not Statements[citizenid][account] then Statements[citizenid][account] = {} end
       Statements[citizenid][account][#Statements[citizenid][account] + 1] = newStatement
   ```
   **后果**：子账户（例如名为 `test` 的 Shared 账户）的实时交易流水被强行存入了 `Statements[citizenid]['test']` 的用户个人分区中。这导致该子账户的其他共有成员无法实时在界面中看到该交易。

2. **服务器启动阶段 (SQL Loading Thread)**：
   ```lua
   -- 从数据库还原加载所有流水时
   if statement.account_name == 'checking' then
       if not Statements[statement.citizenid] then Statements[statement.citizenid] = {} end
       Statements[statement.citizenid][statement.account_name][#Statements[statement.citizenid][statement.account_name] + 1] = statement
   else
       -- 所有非 checking 账户的流水，直接存入全局账户分区
       if not Statements[statement.account_name] then Statements[statement.account_name] = {} end
       Statements[statement.account_name][#Statements[statement.account_name] + 1] = statement
   end
   ```
   **后果**：重启服务器后，子账户 `test` 的流水又被从全局对象 `Statements['test']` 中读取。

3. **数据销户残留漏洞 (Account Deletion & Ghosting)**：
   当玩家在柜台删除（Close Account）子账户时，旧版清理逻辑仅执行了：
   ```lua
   Statements[accountName] = nil
   MySQL.rawExecute.await('DELETE FROM bank_statements WHERE account_name = ?', { accountName })
   ```
   由于游戏实时交易期间数据错误地积压在 `Statements[citizenid]['test']` 分区中，**这部分内存对象在销户时从未被清除**。
   当玩家在未重启服务器的情况下，重新创建一个**重名子账户**（如仍叫 `test`）时，系统读取了未被完全消灭的 `Statements[citizenid]['test']` 脏数据，导致旧账户的历史交易记录“幽灵般”复活在全新账户的账单上。

## 2. 系统重构方案 (Refactoring & Implementation Standards)

本版本对以上问题实施了彻底的代码重构与架构净化：

### 2.1 彻底重构对账单数据结构

我们将对账流水的内存归属进行了大一统的边界划分：**只有玩家 Checking 账户属于个人（以 `citizenid` 隔离），所有子账户（Shared）、企业账户（Job）、帮派账户（Gang）皆属于全局（以 `accountName` 直接检索）**。

在 `CreateBankStatement` 服务端函数中，重构存储路由逻辑为：
```lua
if account == 'checking' then
    if not Statements[citizenid] then Statements[citizenid] = {} end
    if not Statements[citizenid]['checking'] then Statements[citizenid]['checking'] = {} end
    Statements[citizenid]['checking'][#Statements[citizenid]['checking'] + 1] = newStatement
else
    if not Statements[account] then Statements[account] = {} end
    Statements[account][#Statements[account] + 1] = newStatement
end
```
此结构完美与 MySQL 冷启动加载逻辑对齐。这样在删除账户执行 `Statements[accountName] = nil` 时，内存中的所有残留流水都会被毫无漏洞地彻底释放，从根本上杜绝了对账流水的“鬼混”现象。

### 2.2 完全停用并净化物理银行卡与 ATMs

根据服务器轻量化运营规划，我们将全服交互点收缩为**柜台柜员（Teller-Only）模式**。后续的移动转账将直接使用手机完成。因此，本版本完全废除了物理银行卡和 ATM 系统：

1. **废弃卡片与 ATM 服务端机制**：
   - 彻底关闭 `CreateUseableItem('bank_card')` 物品使用接口，防止玩家在背包中双击卡片。
   - 销毁 `qb-banking:server:orderCard`（办卡）和 `qb-banking:server:openATM`（ATM认证）两个服务端 Callback，物理阻断恶意脚本的注入攻击。
2. **清除客户端卡片操作与 ATM 功能**：
   - 清除 ATM 交互线程、进度条及 ATM 实体识别。ATMs 将完全作为无实体的街景模型存在。
3. **前端 UI 界面深层净化 (Svelte UI Refactor)**：
   - **BankDashboard.svelte**：彻底从 Svelte 组件中移除办理物理卡片（"Order Physical Debit Card"）按钮、相关表单状态及 NUI Callback 请求。
   - **App.svelte**：移除 ATM 视图组件的依赖引入、状态机分支，禁止通过任何方式路由至 `atm` 状态，确保加载到游戏 NUI 的始终只有纯净的 Maze Bank 柜台面板。

## 3. 测试验证手册 (Test Suite & Verification Guide)

为保证本次重构代码干净、逻辑无缺陷，请测试工程师按照以下测试集进行严格的单体与联调测试。

### 测试用例 3.1：柜台柜员基础金融与对账单一致性测试

* **前提条件**：玩家登录服务器，身上有 $10,000 现金，Checking 账户有 $5,000 存款。
* **操作步骤**：
  1. 走向任意 Maze Bank 柜台，按下 `E` 或使用 `ALT`（第三眼）唤起柜台界面。
  2. 验证当前 Pocket Cash 是否准确显示为玩家身上的物理现金金额。
  3. 执行 **存款操作**：向 Checking 账户存入 `$1,000`，填入备注 `Checking Deposit Test`。
  4. 执行 **取款操作**：从 Checking 账户取出 `$500`，填入备注 `Checking Withdraw Test`。
  5. 检查页面下方的 `TRANSACTION STATEMENTS`。
* **预期结果**：
  - 存款后，主页面右上角 Pocket Cash 减少 $1,000，Checking 余额增加至 $6,000。
  - 流水历史中新增绿色带箭头记录：`+$1,000`，备注准确显示为 `Checking Deposit Test`。
  - 取款后，Pocket Cash 增加 $500，Checking 余额降为 $5,500。
  - 流水历史中新增红色带箭头记录：`-$500`，备注准确显示为 `Checking Withdraw Test`。

### 测试用例 3.2：子账户开户、对账与销户退款闭环测试

* **操作步骤**：
  1. 在左侧 sidebar 的 `Create New Account` 区域，输入新账户名称为 `Project-A`。
  2. 设置账户类型为 `Shared`，初始存入金额（Initial Deposit）输入 `$2,000`。
  3. 点击 `Open Account` 开户。
  4. 检查 Checking 余额和左侧新卡片 `Project-A` 的余额。
  5. 切换到 `Project-A` 账户，进行一次存入 `$500`（备注：`A-Deposit`）和取出 `$200`（备注：`A-Withdraw`）的操作。
  6. 检查 `Project-A` 的对账流水。
  7. 进入 `Project-A` 的 `Access Control` Tab，在 `Danger Zone` 中点击 `Close Account & Refund`。
  8. 重新切换检查 Checking 账户余额。
* **预期结果**：
  - 开户成功后，Checking 余额应自动划扣 $2,000。左侧列表新增 `Project-A` 卡片，余额为 $2,000。
  - `Project-A` 的流水历史**仅有**一条记录：`+$2,000`（Initial deposit）。
  - 存取款操作后，`Project-A` 余额更新为 $2,300，且其流水完美显示上述两条对应操作。
  - 点击销户后，`Project-A` 卡片从 sidebar 消失。
  - 销户退款将全额原路返还，Checking 余额立即增加 $2,300，且 Checking 流水单中新增一条备注为 `Refund from closure of Project-A` 的 `+$2,300` 存款对账记录。

### 测试用例 3.3：重名账户历史对账单“幽灵”复活防漏测试（核心漏洞验证）

* **前提条件**：完美通过 **测试用例 3.2**，完成了 `Project-A` 账户的创建、多次交易、以及销户退款动作。
* **操作步骤**：
  1. 不重启服务器，保持在线。
  2. 再次来到柜台，在 `Create New Account` 区域输入**一模一样**的账户名称：`Project-A`。
  3. 初始注入资金填写 `$100`。
  4. 点击 `Open Account` 开户。
  5. 点击左侧新生成的 `Project-A` 卡片账户。
  6. 仔细观察下方的 `TRANSACTION STATEMENTS`。
* **预期结果**：
  - `Project-A` 开户成功，余额显示为稳定的 `$100`。
  - 下方的流水单**有且仅有**一条新开户记录：`+$100` (Initial deposit)。
  - 之前旧 `Project-A` 账户产生的 `$2,000` 开户流水、`$500` 存款、`$200` 取款记录**完全消失，无任何串卡、残留或混淆显示**。

### 测试用例 3.4：银行卡停用与 ATM 彻底失效测试

* **操作步骤**：
  1. 进入柜台界面，切换至任意子账户，选择 `Access Control` 面板。
  2. 观察页面右下角区域。
  3. 通过管理员指令获取一张 `bank_card` 道具，放入背包。
  4. 在背包中双击使用 `bank_card`。
  5. 走近街头任意一台 ATM 机，使用 `ALT`（第三眼）试图聚焦 ATM。
* **预期结果**：
  - 子账户的管理面板中，原本存在的办卡区域（`Order Physical Debit Card` 按钮）已被**完全移除，无残留阴影或占位符**。
  - 在背包中双击 `bank_card` 道具无任何响应，客户端与服务端控制台无任何非法事件报错。
  - 对准 ATM 实体持 ALT 扫描，无任何“打开ATM”选项浮现。ATM 沦为纯净的街景装饰模型。

## 4. 交付与维护规范 (Maintenance Guidelines)

1. **零死角重构审查**：后续维护如需恢复部分账户的共享交易流水，须始终维持 `Statements[accountName]` 的全局分区管理，严禁私自倒退回以 `citizenid` 混合存储的模式。
2. **NUI 一键构建**：在修改 `web/` 下的 Svelte 界面后，必须使用 `npm run build` 打包。提交前请确认 `html/assets` 下的文件 Hash 已正确刷新。

## 5. 对公与共享账户多级审批与回避机制设计规范 (Advanced Approval & Audit Design)

根据 v0.3 实机测试反馈，对公账户（Job/Gang）和玩家共享账户（Shared）在大额资金变动时，单纯依靠实名流水表态仍无法防御“下线期爆仓”或“单人资金垄断”的风险。因此，确立如下未来与 v0.4 手机系统 / v0.6 领袖系统对接的审批机制设计规范：

### 5.1 审批回避与分权控制 (Checks and Balances)
1. **去直取化（No Direct Withdrawals）**：
   - 职业/组织内的 1、2 级基层成员（On-Duty）无法看到公共金库余额（显示为 `***`），且界面不提供提现与转账按钮。仅提供 `+ 发起支取申请 (Request Funds)` 按钮。
   - 所有支取必须提交金额和明确用途，生成挂起（`pending`）账单并锁定对应额度。
2. **多级审批权（Approving Authority）**：
   - 只有 3、4 级管理层（如警长、局长）可以查看公共金库总余额，并在 `Approvals`（审批工作台）中进行批示。
3. **审批回避制（Self-Approval Prevention）**：
   - **核心安全原则**：即使是 3、4 级管理层玩家，当他们自己需要支取对公资金时，其申请同样必须进入队列，且**其本人无法批准自己的申请**。必须由另一个拥有批示权的管理层玩家上线审计并签字同意后，资金才可解冻到账，彻底避免一家独大。

### 5.2 共享账户分权控制
- **所有者（Owner）**：拥有该账户的绝对支配权，直接存取/转账无需审批。
- **授权协作者（Collaborators）**：只具备 `发起支取申请` 权限，申请将自动推送给所有者，必须由所有者在界面或手机 App 中点击同意后划拨。

### 5.3 离线安全机制与挂起队列 (Persistent Queue)
- 所有支取申请将通过 `bank_approvals` 数据库表进行永久化挂起。
- 审批者上线时，系统会自动在游戏内弹出提示，并在 Maze Bank 柜台侧边栏及右上角渲染红色的**未审批数字气泡 (Badge)**，确保离线期间的资金异动绝不遗漏。
