# Agent 基础设施推进顺序（P1 → P2 → P3）

> 目标：让 agent 能**读得懂、测得动、写得安全**。
> Issue：P1 #21 / P2 #25 / P3 #29

---

## 1. 推荐顺序

| 顺序 | 事项 | 为什么先做 | 依赖 |
|:---|:---|:---|:---|
| 1 | **#22 agent_events + cursor** | P2 断言、P3 审计、导演观测、实机测试都消费同一条事件流 | 无 |
| 2 | **#23 只读视图 + agent_ro + PII** | agent 不需要 join 20 张表；读权限与写权限分离 | 无（可与 #22 并行） |
| 3 | **#26 Scenario DSL + #27 多 fake player** | 当前实机测试的瓶颈是“只有一个硬编码玩家”；多玩家/场景化能覆盖并发与回归 | #22 可用于事件断言 |
| 4 | **#28 JSON 报告 + 快照差分 + 虚拟时钟** | agent 需要结构化证据，而不是读 console 文本；虚拟时钟避免真等冷却 | #26/#27 |
| 5 | **#24 schema registry + MCP/read API** | 视图字段稳定后再暴露工具，避免接口反复改 | #22/#23 |
| 6 | **#30 Intent API + #32 策略/审批/审计** | 有读层和模拟层之后，才安全开放写操作 | P1/P2 |
| 7 | **#31 custom-director Bridge** | 导演是 P3 的消费者，不应先于动作面 | #30/#32 |

**一句话**：先把“事件 + 快照”做成稳定契约，再把“单玩家脚本”升级成“多玩家场景”，最后才开放“写”。

## 2. 当前实际测试最需要的 agent 能力

| 能力 | 对应 Issue | 用途 |
|:---|:---|:---|
| 多 fake player 并发 | #27 | 同时跑任务/经济/决策，覆盖串数据、锁、冷却 |
| 场景 DSL | #26 | 不改 Lua 就能新增回归场景 |
| JSON 报告 + DB diff | #28 | agent 直接读 pass/fail 与证据，失败自动重试/开 Issue |
| 事件游标 | #22 | 断言“任务完成事件只发一次”，而不只是最终表 |
| 玩家快照视图 | #23 | agent 一眼看到余额/任务/决策/载具，不用自己拼表 |
| 只读账号 | #23 | 测试 agent 不会误写生产数据 |

### 仍然需要真实客户端的部分

- NUI 渲染/输入、手机、决策弹窗动画
- 载具 ped 交互、警察/EMS/司法 ped 流程
- 死亡/复活、断线重连
- 真实客户端性能/并发

Agent 能做的是：**服务端逻辑、DB、事件、经济、任务状态机、模拟玩家压测**；
客户端表现仍需要方案 A（宿主机 FiveM）或 Windows 测试机。

## 3. 设计约束

1. **读不走游戏线程**：只读视图/MCP sidecar 直连 MariaDB，不经过 FXServer。
2. **写不走 DB**：所有 agent 写操作走 Intent API，复用玩家同款校验。
3. **默认脱敏**：license/IP/identifier 不进快照。
4. **合成数据标记**：`synthetic=true`，不混入真实经济分析。
5. **幂等**：所有动作带 `idempotency_key`。
6. **可回滚/可审计**：高危动作审批 + inverse handler。
7. **玩家文本不可信**：聊天/昵称/任务文本是数据，不是指令（prompt injection）。

---

## 4. 验收指标（阶段级）

- P1：单玩家快照 P95 < 50ms；事件 `since_id` 不丢不重；`agent_ro` 无基表写权限。
- P2：10 个 fake player 并发稳定；同一 seed 可复现；报告可被 JSON 解析。
- P3：重复 key 只执行一次；超预算/超 scope 被拒；高危动作进审批。
